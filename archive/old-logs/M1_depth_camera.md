## 会话 2026-10-24 19:05 — M1 启动：排查 4 向深度相机无数据问题（P1）

### 操作与结果

1. 起点：上次会话部署 4×depth_camera（320×240@5Hz，far=12m）后，Python 订阅 `/depth_*/depth_image` 10s 无消息（P1）。
2. 检查 VM 状态：发现上次会话的 demo 中 **gz sim 服务端/GUI 已退出**（日志 480 行："process has finished cleanly [pid 170615]"，非崩溃；ROS 节点空转）。附带发现 `pgrep -c -f 'gz sim'` 自匹配陷阱（计数含 bash 包装进程），后续 pgrep 均加 grep -v 过滤。
3. 停残留 demo → 重启（`bash ~/m1_restart.sh`，start_demo auto_voice:=false，pid=181665）→ T+10s/T+20s 两次确认 server+gui 存活，`gz topic -l` 出现深度话题：`/depth_front` 与 `/depth_front/points`（**没有 `/depth_image` 子话题**）。
4. `gz topic -i`：`/depth_front` 类型 gz.msgs.Image（有发布者），`/depth_front/depth_image` 无发布者。
5. Python 订阅 `/depth_front` 实测：320×240，pixel_format_type=13（32FC1），307200 字节=320×240×4；按 32FC1 解析：有效深度 18987/76800 点，min=0.88 / max=9.15 —— **真实场景深度**。
   - 踩坑记录：gz.msgs10 Image 的格式字段名是 `pixel_format_type`（非 pixel_format）；统计消息模块是 `gz.msgs10.world_stats_pb2.WorldStatistics`（非 statistics_pb2）。
6. 四向全检 + RTF（`bash ~/m1_all.sh`）：
   - front: 有效 18987 点 min=0.88 中位=2.27 max=9.15
   - left:  有效 34661 点 min=0.08 中位=1.44 max=5.14
   - right: 有效 28941 点 min=0.24 中位=1.25 max=11.51
   - back:  有效 56654 点 min=0.10 中位=0.72 max=5.32
   - **RTF = 1.00**（sim 415.8s / real 418.5s）—— 4 深度+RGB+雷达+GUI 全开性能达标（方案 Gate-1 RTF≥0.8 ✓）

### 结论

- **P1 已解决**，根因：Gazebo Harmonic 8.15 的 depth_camera 传感器把 32FC1 深度图发布在**基础话题**（`/depth_front` 等），不产生 `/depth_image` 子话题；上次探针订阅了错误的话题名。服务器"无数据"表象的另一因素是该次运行的 gz sim 已先行正常退出（疑似窗口被关闭，非崩溃；本次重启后稳定）。
- 登记新坑（追加到 TaskPlan §5 环境速查）：①深度话题名=基础话题；②Image.pixel_format_type；③world_stats_pb2。
- 方案 §4.1 排障步骤①②③④⑤全部执行完毕且通过（无需修改传感器配置、无需降级路径）。
- 下一步：开发 depth_percept 感知层节点（方案 §4.2）。
