## P72 底盘运动学标定与闭环验收（22:35–23:40）

**定位根因（上一次的判断是错的）**：不是 `wheel_radius`/`wheel_separation` 错，是**车根本立不住**。
- `gz model -p` 打的 RPY 有欧拉角分解歧义，不能直接读；改从 `/world/follow_world/pose/info` 取**四元数**自己算：robot 四元数 `(0.0960,0.2490,-0.3466,0.8993)` → `pitch=asin(2(wy−zx))` = **0.5403 rad = 31°**，roll≈0。且复位后是 0、行驶后是 0.54 → **跑起来才发生**。
- 几何：质心 x=0，轮轴 x=0，支撑点只有「两轮 + 一个后支撑脚 caster(x=−0.12)」→ 支撑多边形 `x∈[−0.12,0]`，**质心正好落在前沿**，零稳定裕度 ⇒ 一有扰动就绕轮轴前倾到车头触地（理论 atan(0.08/0.15)=28°，实测 31°）。前倾后车头吃载荷、轮子失法向力 → 全是横滑。这才是"1.155m/1.385m 是横滑""角速度 1.48×"的真因。

**三处一直没生效的 SDF 写法**
- `<xyz resolved_frame="child">`：`resolved_frame` **不是 SDF 属性**，gz 告警后忽略。轮 link 绕 X 转了 +90°，其局部 Z = 机体系 **−Y** ⇒ 正轮速 = 后退（命令 +0.8 得 −135.6°）。改成 `<xyz>0 0 -1</xyz>`。
- `<axis><limits>` 元素名错（应为 `<limit>`），同样被忽略。
- `caster` 无 joint 的游离 link。

**改法**：caster 补 revolute joint（轴 **`0 1 0`** —— 不能照抄轮子的 `0 0 -1`，caster link 没旋转、其 Z 是竖直轴，照抄会变成绕竖轴打转的假万向轮）；再补 `caster_front`(link+joint) 让支撑多边形 `x∈[−0.12,+0.12]`、质心居中。person 三处同病同修。

**标定结果（/odom = gt_tf 真值）**：直行 0.200 m/s（指令 0.20，**1.00×**，y 漂移 0.000m）；原地转 **+0.50 rad/s**（符号正确、幅值精确）；全程 **pitch=0**。→ wheel_radius/separation **不用改**。

**Nav2 闭环**：置 `/nav2_active=true` + `NavigateToPose(2.50,0.60)` → `SUCCEEDED`，终点误差 **0.211m**（默认容差 0.25），路径 2.09m/12.7s。需求③的前置条件解除。

**120s 全量评测 `t4_p72.json`**：居中 |brg|≤10° **98.2%**（中位 3.4°，仅 front 样本 99.1%）、≤5° 75.8%、可见率 93.2%、front 占比 92.4%、相机分布 front2257/left14/back6/none165、切换 3 次均值 2.33s、丢失 2 次均 2.6s（都在进 GOTO 前恢复）、**min_gap 0.416m 撞击 0 擦碰 0**、距离中位 1.10m（带内 53.6%，p90 1.61）。对比旧数据 91.9% → **98.2%**。

**剩余问题（下一步）**：距离滞后是**控制律**问题。人步速 0.25~0.65（均值 0.45），follower 实测 cmd_v 中位仅 0.113 → 纯比例控制 `v=k(d−1.0)` 的稳态必然停在 `1.0+0.45/k`，与实测 1.1~1.6m 吻合。修法：**加速度前馈**（从 `/person/odom` 或视觉历史窗估人速，`v_cmd=k(d−1.0)+v_person·cos(相对方位)`）优先于调增益。

**可复用教训**
- 判断机器人"走不准"之前，先确认它**站得直**：读世界四元数算 pitch，别读 `gz model -p` 的 RPY 打印。
- SDF 里写错的属性/元素名 gz 只告警、然后**静默忽略** → 一定要 `grep -c` 日志里的 `Warning [Utils.cc`，别假设它生效。
- `pkill -f 'p72_sampl[e]r'` 匹配的是命令行里的 `p72_sample.py`，**匹配不上** → 采样器会跨测试继续写同一个文件，把两段数据混在一起。杀进程用命令行里真实出现的字符串。
