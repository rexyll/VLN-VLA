# 跟随机器人「原地打转」问题：诊断与修复报告

**目标**：机器人经 front/left/right/back 四方位相机以 2 张/秒抓拍，快速找到目标、把朝向调整到目标偏离 front 中线 ±15° 内、再按距离决定是否移动。

**结论**：问题不是单一原因，而是**感知层的航向角公式算错** + **车体模型三处硬伤** + **控制层绕障/速度逻辑越权** 三层叠加。修复后机器人能稳定对正（±15° 带内）、按 1.0 m 目标距离接近，并具备丢失后主动搜索能力。

---

## 一、根因（按因果权重排序）

### 1. 航向角公式错误 —— 全局性、最致命

`yaw_of()` 的分母写成了 `1 - 2(y² + x²)`，正确值是 `1 - 2(y² + z²)`。

```python
# 错误（原代码，4 个节点全中）
yaw = math.atan2(2*(q.w*q.z + q.x*q.y), 1 - 2*(q.y*q.y + q.x*q.x))
# 正确
yaw = math.atan2(2*(q.w*q.z + q.x*q.y), 1 - 2*(q.y*q.y + q.z*q.z))
```

用 `set_pose` 打已知角度验证：**设 90° 读成 45°，设 180° 读成 0°，机器人实际朝 141° 走而日志报 32°**。

后果是致命的：机器人的真实航向、目标相对方位、目标世界坐标全部失真，控制器算出"转角"和实际需要的转角根本不是一回事 —— 于是**无论朝哪转，误差都不收敛，表现为原地打转**。这解释了为什么调 PID、调速度都没用。

涉及文件：`follower.py`、`person_vision.py`、`depth_percept.py`、`person_walk.py`。

### 2. 模型三处硬伤（在 `work_area.sdf`）

| 缺陷 | 现象 | 修复 |
|---|---|---|
| `caster` link **没有任何 joint**，是游离刚体 | 实测飞到 `(-5.106, +0.048, +3.087)`，车尾无支撑，车身仰 31°，驱动轮离地空转 | 补 `<joint name="caster_joint" type="fixed">`，摩擦 `mu 0.02` |
| 驱动轮 `roll=+1.5707` 使关节轴落在车体 −Y | DiffDrive 把 (v, w) 整体取反：`w=+1.0 → −0.78`，`v=+0.3 → −0.204` | 保持几何，关节轴写 `0 0 -1` |
| 驱动轮 x=0 与质心同线，支撑多边形退化 | 加速时后仰、原地转向时打滑 | 驱动轮前移 0.06 m |

### 3. 障碍表有 4 个"幽灵障碍"（控制层最大干扰源）

代码里硬编码 7 个障碍，而 `work_area.sdf` 里只有 **3 根立柱**真实存在，半径还统一多写了 0.07：

```python
# 修复前：只有 (0.5,-3.2)/(-4.2,-2.5)/(2.2,4.6) 是真的
OBSTACLES = [(3.5,2.0,0.57), (-3.0,3.2,0.67), (0.5,-3.2,0.47),
             (-4.2,-2.5,0.57), (4.2,-3.0,0.37), (-1.5,-4.5,0.62), (2.2,4.6,0.42)]
# 修复后：与 SDF 一一对应
OBSTACLES = [(0.5,-3.2,0.40), (-4.2,-2.5,0.50), (2.2,4.6,0.35)]
```

更糟的是绕障**越权**：它会直接下发 `v=min(0.6, …)`、`w=±1.8~2.2`，把对正带和接近速度全部丢掉。日志里 `指令v=+0.60`、`w=±3.2` 都来自这一段 —— 机器人对着空气猛打方向，看起来就像"原地打转"。

两处修复：剔除幽灵障碍 + 绕障只允许"限速 + 偏转"，不得越过接近速度与对正带约束。

同时 `_waypoint()` 的线段距离判定把**目标身后**的障碍也算成挡路（`seg_dist` 把投影参数夹到 [0,1]），补了投影参数 `t ∈ (0.05, 0.97)` 的硬约束。

### 4. 人的逃逸阈值与跟随目标距离直接冲突

`person_walk.py` 在机器人距离 **< 1.3 m** 时进入 ESCAPE 逃跑，而跟随目标距离是 **1.0 m**。
机器人刚走到目标距离，人就必然跑 —— **结构上永远追不上、永远停不下来**。改为 `< 0.85 m`（略小于 `track_dist − tol = 0.9`）。同时清掉该文件里另外 4 个幽灵障碍。

### 5. 搜索链路是死代码

```python
self._vis_mono = time.monotonic()   # 每帧都刷新，包括 detected=false
...
if ... and now - self._vis_mono > 2.0:   # 所以这个条件永不成立
```

实测 **24 次"四相机视野内均无人"，0 次触发搜索**。改为只在 `detected=true` 时刷新检出生效时刻。

### 6. 控制细节

- **速度平滑升降共用 0.9 m/s²**：切进 ALIGN 时目标速度已置 0，`self.v` 却缓慢收敛，机器人边转边滑（日志 `指令v=+0.26`）。改为加速 1.2 / **减速 4.0 m/s²**，并用真实 dt。
- **距离环前馈过强**：`v_cap = max(0.2, pspd+0.25)` 在目标快跑时抬到 0.9 m/s。而深度只有 5 Hz、又容忍 0.8 s 陈旧，等于最多 0.5 m 盲走 —— 实测冲到 0.58 m（安全距 0.65），差点撞人。改为按"视觉时延内不得冲进安全距"限速：`v ≤ (dist − guard_d)/0.8`，近距离不吃人速前馈。
- **对正段允许边走边转**：偏差 ≤34° 时给 `0.6 × approach_speed` 的前进速度。纯原地旋转会让人越跑越远，实测 90 s 内进出对正 44 次，形成"走走停停追不上"。
- **主相机改为 front 优先**：只有 front 的 bearing 与"±15° 中线"判据同基准，sticky 逻辑会让 bearing 长期挂在左右相机的掠射角上。
- 位姿丢失告警从 20 Hz 限流到每 3 s 一次（原来会淹没整个日志）。

## 二、一个重要的反向教训：测量工具也会骗人

标定脚本 `tmp_rate2.py` 里的 `yaw_of` 沿用了同一个错误公式。这个错误公式在 `yaw≈0` 处导数正常，转到 90° 附近导数趋近 0，**长距离累加会系统性低估角速度** —— 我据此一度判断"实测角速度只有指令的 49%"，差点去改 SDF 运动学。

修好工具、并且每次测试前用 `set_pose` 复位到空地（避免顶墙造成假低速）后复测：

| 指令 | 实测 | 比例 |
|---|---|---|
| v = 0.30 | 0.300 | **1.00** |
| v = 0.60 | 0.600 | **1.00** |
| w = 1.00 | 1.000 | **1.00** |
| w = 2.00 | 1.689 | 0.84（高速端轻微打滑，可接受） |

**被控对象本身是准的**，SDF 运动学不需要再改。

## 五、运维注意（很容易踩）

**在 SSH 会话里启动仿真必须先 `export DISPLAY=:0`**。gz sim 默认带 GUI，`DISPLAY` 为空会让 Qt 初始化失败，进程以 `process has finished cleanly` 立刻退出 —— 此时各 ROS 节点仍在跑，日志看着正常，但位姿和图像全是空的，很容易被误判成算法问题。

```bash
export DISPLAY=:0
ros2 launch vla_follow demo.launch.py auto_voice:=false
```

诊断命令：
```bash
python3 tmp_probe.py       # 3 秒内能否收到 /world/follow_world/dynamic_pose/info
```
