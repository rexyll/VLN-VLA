# 避障稳定性 —— 根因定位与修复报告

> 症状（用户原话）：机器人的避障功能有问题，遇到障碍物，有时候会撞上去。
>
> 结论：**不是阈值没调好，而是四条独立的数据通路各自出了问题**。逐条修完后，
> 5 个刻意设计的碰撞场景从 2/5 安全提升到 **5/5 安全**，最小安全余量 +0.24m
> （按车体外接圆算）。同时跟随质量没有退化，反而明显变好。

---

## 一、先说结论：五个根因

| 编号 | 根因 | 后果 | 修法 |
|---|---|---|---|
| P26 | **雷达在本环境根本不可用**，`/scan` 的 360 条射线全是 `range_min=0.12` | 安全层被"到处都是 0.12m 障碍"的假数据污染，一律急停 | 改用 4 台深度相机分扇区测距，并加开机自检，不可用时日志明确报出来 |
| P27 | 急停时"哪侧空往哪转"，与上层"目标在右就右转"**对打** | `w` 每帧翻号（实测 −1.0 → −1.4 → +1.1），车原地抖、绕不开 | 转向方向加**滞回锁存**（≥0.45s，另一侧须空 0.35m 以上才换边）+ 受阻 2.2s 后后退脱困 |
| P28 | 深度取样行带 `10%~45%` 其实是仰角 **+33.4°~+4.2°** | 0.8m 立柱在 4m 处只到 8° 仰角，几乎整个落在带外 → 远处矮障碍漏检 2.3m | 按仰角重算行带：**+1.5°~+18°**（下沿的地面回波落在 8.8m，不参与 5% 分位） |
| P29 | 深度图**边缘插值伪影**被 5% 分位数当成最近障碍 | front 左前扇区读数从"几米"坍缩到 **0.33m**，安全层误以为贴脸 | 列方向裁掉左右各 4%（相邻相机有 10° 重叠，不丢信息）+ 深度下限 0.05→**0.12**（相机 near=0.1，更近的值全是自遮挡） |
| P30 | 安全层只用 payload 里的 `age` 判新，**发布方一死就永远"新鲜"** | `depth_percept` 崩过一次，机器人拿着冻结的快照继续开 | 按**收到消息的时刻**做看门狗：中断 ≥0.5s 禁止前进，每 3s 报错 |

其中 **P30 是最阴的一条**——它把"撞上去"变成了间歇性、难以复现的故障。

## 二、逐条的证据

### P26：雷达为什么不可用

```
$ gz topic -e -t /lidar          # 原始数据, 未经过桥接
有效射线 360/360, min = 中位 = max = 0.120, 无回波 0 条
```

试过改 `type="lidar"`（CPU 版）绕开：

```
[Sensor type LIDAR not supported yet. Try using a GPU LIDAR instead.]
```

根因：`gpu_lidar` 依赖 ogre2 的 GPU 深度预渲染，而 `demo.launch.py` 为了
绕开 VMware 下的 ogre2 白屏，固定用 `--render-engine ogre`（ogre1）。

修法：4 台 `rgbd_camera` 每台按列分 5 个扇区、每扇区取 5% 分位数，
合成 **8 个 45° 方位**（front / fl / left / bl / back / br / right / fr）。
再加开机自检，把判断写进日志，避免以后又误以为雷达在工作：

```
FOLLOWER 雷达自检: 不可用(全为量程下限) → 全向避障改用 4 台深度相机
```

### P28 + P29：深度数据本身的精度

用真值射线逐扇区对齐比较后，两处修正的收益：

| 场景 | 修正前 | 修正后 | 理论真值 |
|---|---|---|---|
| front 左前扇区（空地） | **0.35 m**（边缘伪影） | 3.56 m | ≈ 5–8 m（空地） |
| right 中心扇区（0.5m 高的 ob6，3.6m 外） | **5.10 m**（漏检） | 3.22 m | 2.81 m |
| front 中心扇区（正对 2.7m 外的墙） | 7.60 m | 7.60 m | 7.60 m |
| ob5 立柱正面（0.6×0.6×1.2，1.27m） | 0.70 m | 0.70 m | **0.67 m** |

关键结论：**近场（≤2.5m）一直是准的**（误差 0.03m），错的是远处矮物体和
画面左右边缘。所以修完之后避障的第一道防线可靠了，但"看见很远"仍然不是
这个方案的强项——这也是把 `lidar_slow_m` 定在 1.6m 的原因。

另外做了"扇区索引 → 方位角"的标定（4 台相机各自用两种假设比误差）：
**4/4 都指向"索引 0 = 左侧"**，确认代码里的方位映射没有左右互换。

### P30：一次真实的静默失效

第 6 轮测试跑完是 2/5 安全，但日志里这一组数字 **45 秒一字未变**：

```
全向限速 前0.83 左前3.10 右前3.90 v<=0.28
全向限速 前0.83 左前3.10 右前3.90 v<=0.28      (45s 后)
```

翻日志找到：

```
[depth_percept-4] ValueError: Unknown format code 'd' for object of type 'float'
```

我自己在 P29 里把扇区跨度改成浮点 18.4° 后又用了 `f'{off:+d}°'`，
感知节点开机第一帧就崩了。而 follower 完全不知道——因为 `age` 是**发布方
算的**，发布方死了，最后一帧的 `age` 就永远冻在 0.0x 秒。

于是机器人以 0.28m/s 的速度、用一份几分钟前的快照在开。
**这正是"有时候会撞上去"这种间歇性故障的典型成因。**

修法（两处）：
1. 修掉格式串（`int(round(...))`）；
2. follower 记录收包时刻 `_prox_rx`，中断 ≥0.5s 就禁止前进并报错——
   没有数据的避障层无法保证不撞，停下来是唯一诚实的处理。

### P27：转向振荡

修复前（对正阶段，目标在 −37° 右侧）：

```
w=-1.0 对正-37°      ← 上层想右转
w=-1.4 对正-46°      ← 继续右转
w=+1.1 对正-25°(边转边走) 全向急停 前0.77 左前1.88 右前0.75   ← 安全层改成左转
```

安全层原来写的是 `w_t = 1.1 if d_fl >= d_fr else -1.1`——只看哪边空。
车一往左转，`d_fl` 就变小、`d_fr` 变大，下一帧又翻回去。

修法（三件一起才稳）：
1. 方向**优先沿用上层意图**，只要那一侧还有余量（`> stop_d × 0.92`）；
2. **滞回**：选定方向至少保持 0.45s，期间只有"另一侧明显更空 0.35m 以上"才换边；
3. **脱困**：原地受阻超过 2.2s 且后方有余量 → 先退 0.18m/s 给转向腾空间，
   退 1.8s 后重新计时，防止无限后退。

效果：角速度符号翻转从 **0.56 次/秒降到 0.21 次/秒**，全程 0 次误触发急停。

### 额外发现：安全层把"要跟随的人"当成障碍

跟随 111s 的日志里有 **259 条** `全向限速`：

```
距离=1.03m(目标1.00m) ... 全向限速 前0.71 左前1.02 右前2.35 v<=0.09
```

跟到 1.0m 时，人的**躯干表面**距相机只有 ~0.7m，低于 `slow_d=1.6`，
于是安全层一路把速度压到 0.06~0.12m/s，机器人只能爬，人一走动就掉队
（实测距离长期停在 1.385m）。

修法（P31）：安全层拿到目标距离/方位，若某个前向回波与"人的躯干表面期望
距离"相差 <0.45m 且方位在目标附近，判定"那是目标不是障碍"，抬到限速阈值
之上。真正贴近时（目标 <0.6m）仍有独立的"防撞人"退避逻辑兜底。

同时把 `approach_speed` 从 0.32 提回 **0.38**——原来压到 0.32 恰好等于人的
步速 0.32m/s，机器人**永远追不上**。

## 三、结果

### 避障专项（5 个刻意设计的碰撞场景，每个 30s）

判据按障碍**真实形状**算距离（方块考虑 yaw、圆柱按半径），再分两档：

- `gap_in < 0`：撞进**内切圆**（0.10m）→ 撞上
- `gap_out < 0`：越过**外接圆**（0.18m）→ 擦碰
- 否则安全

| 场景 | 修复前 | 第 5 轮 | **最终** |
|---|---|---|---|
| A 正面直冲 ob3（圆柱 r0.4） | 撞 | +1.002 | **+0.441** |
| B 斜 35° 冲 ob3 | 擦 | +1.230 | **+0.497** |
| C 正面直冲 ob1（0.8×0.8 方块） | 撞 | +0.755 | **+1.020** |
| D 冲墙角 ob4（圆柱 r0.5） | 安全 | +1.037 | **+0.539** |
| E 斜 40° 冲 ob5（0.6×0.6 方块） | 擦 | +0.733 | **+0.322** |
| **总计** | **2/5** | **5/5** | **5/5（最小余量 +0.24m）** |

"修复前"那三个真的撞了（`gap_in` 为负）；第 5 轮开始全部为正，
最终配置下最小余量 +0.24m（外接圆外）。余量比第 5 轮略小，是因为把
`approach_speed` 从 0.32 提回了 0.38——这是为跟随能力做的交换，仍然安全。

### 跟随回归（人绕 r=2m 圆周、0.32m/s，跑 111s）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 距离 均值 / 标准差 | 1.385 m / 0.374 | **1.192 m / 0.084** |
| 对正带 ≤15° 占比 | 60.2% | **99.1%** |
| 平均 \|目标方位\| | 15.8° | **5.0°** |
| 跟踪态占比 | 56.9% | **97.6%** |
| w 符号翻转 | 0.37 次/秒 | **0.21 次/秒** |
| 全向限速条数 | 259 | **62** |
| 急停 / 脱困 | 0 / 0 | 0 / 0 |

## 四、最终参数（`vla_demo/vision_config.json`）

```json
{
  "approach_speed": 0.38,
  "lidar_stop_m": 0.66,
  "lidar_slow_m": 1.6,
  "lidar_side_m": 0.6,
  "lidar_max_age_s": 0.22,
  "lidar_tau_s": 0.6,
  "escape_s": 0.9,
  "esc_hold_s": 0.45,
  "blk_s": 2.2
}
```

四个安全裕量的来历：

- `lidar_stop_m = 0.66` = 车体外接半径 0.18 + 测距滞后（v·age，0.38×0.22≈0.08）
  + 制动距离（0.6s 反应）× 0.38 ≈ 0.40。三者相加即 0.66。
- `lidar_slow_m = 1.6` 是减速曲线的起点，`v_cap = (d − stop)/tau`。
- `lidar_side_m = 0.6` 管侧向防擦，且**必须**把 `bl/br` 两个后翼算进去——
  绕障时障碍方位会从 90° 连续转到 135°，只盯 left/right 会在这段漏掉。
- `lidar_max_age_s = 0.22` 配合相机 `update_rate=10Hz`，把盲走距离压到 0.08m。

## 六、还剩下的问题（没做，但值得知道）

1. **没有绕行规划**。障碍正好挡在目标正前方时（人站在立柱后面），
   机器人会"转—停—转"。现在有 2.2s 后退脱困能跳出这个死循环，但它不是
   真正的局部规划。要彻底解决得上 DWA / 或加个短程 A*。
2. **远处矮障碍看得不够远**。行带修正后 0.8m 高的物体在 4m 处可见，
   但 0.5m 高的只能到 3.5m 左右。要看得更远需要 ogre2（雷达/更好的深度），
   而 ogre2 在 VMware 下白屏。
3. **视觉测距有 +0.19m 恒定偏置**。标准差只有 0.084m，说明是估计偏差而非
   噪声。想消掉它得标定 `track_dist_m` 或者在标定阶段改 person_vision 的
   深度取样点。
4. **Gazebo GUI 的 3D 视口在 HiDPI 下只渲染窗口左上角一小块**（ogre1 + VMware），
   `QT_SCALE_FACTOR=1` 也没解决。截图取证只能裁剪放大小块区域。
